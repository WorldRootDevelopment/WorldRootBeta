# Architecture

The reviewed plan lives here: [WorldRoot Architecture & MVP Plan](https://claude.ai/code/artifact/cc9bf113-c637-4f1f-9e13-183f015e00cc).

Decisions that differ from the plan, or that the plan left open, are recorded below as they are made.

## Decisions

| Date | Decision | Reason |
| --- | --- | --- |
| 2026-10-07 | Local development and tests run on PGlite, an in-process PostgreSQL, when `DATABASE_URL` is unset. | No Docker or PostgreSQL install is needed to run the app or the tests. Production uses a PostgreSQL server through the same Drizzle schema and migrations. |
| 2026-10-07 | The outbox is drained by a polling loop in `apps/worker` using `FOR UPDATE SKIP LOCKED`. pg-boss is deferred until scheduled jobs are needed. | The loop is a few dozen lines, is tested, and works on both database drivers. pg-boss needs a real server and adds nothing until there are scheduled jobs. |
| 2026-10-07 | Handle and adult confirmation are collected in an onboarding step after sign-up, not on the sign-up form. | OAuth sign-ups cannot carry custom fields, so one onboarding step serves every sign-in method. |
| 2026-10-07 | Email verification is not yet enforced. | No email provider is chosen. It must be enforced before any public launch. |
| 2026-10-07 | TypeScript is pinned to 6.x and Next.js to 16.3.x. | typescript-eslint does not yet support TypeScript 7. Next.js 16.4.0 was a day old and failed pnpm's release-age policy. |
| 2026-10-07 | A first slice of communities, roles, worlds, locations and characters was built ahead of phase 2, read-only in the interface, to support a demo community. | A browsable demo was wanted before the scene engine. The services, the copy model and the permission checks are real and tested; the create and edit screens are not built. |
| 2026-10-07 | The embedded database seeds the Star Trek demo community when the web app starts. | The embedded database is single-process, so a separate seed command cannot run beside the dev server. It must not ship to a public deployment: it uses a real franchise setting and a published password. |
| 2026-10-07 | Locations use a parent id only. The `ltree` path column is deferred. | A world's locations are loaded whole and arranged in memory, which is enough until scenes need subtree queries. |
| 2026-10-07 | The server validates and renders rich text with its own small module in `packages/editor`, not with TipTap. | The document schema is a short allowlist, so a hand-written validator and renderer is under 200 lines, needs no DOM on the server, and is safe by construction. TipTap runs in the browser only, configured to produce the same schema. |
| 2026-10-07 | Live updates use an in-process publish and subscribe in the web app, feeding a server-sent event stream at `/api/v1/events`. | It makes posts appear at once with no extra infrastructure, and it works on the embedded database. It reaches only browsers connected to the same process, so running more than one web process needs Postgres notifications behind the same `publish` and `subscribe` functions. A 60-second refresh remains as a safety net. |
| 2026-10-07 | Any participant may post narration. | The plan says "Narrator when permitted" without defining it. Restricting narration is left until a community asks for it. |
| 2026-10-07 | Character biographies and world descriptions stay plain text. Only scene posts use the rich text editor. | Converting those fields means a storage change for every long field. Scenes were the priority. |
| 2026-10-07 | A role manager can grant only permissions they hold, and can change, assign or remove only roles ranked below their own highest role. The Owner role is fixed and cannot be assigned or removed. | Without these two rules, anyone with "Manage roles" could promote themselves to full control. The cost is that ownership cannot be transferred yet. |
| 2026-10-07 | Community settings pages return 404, not a refusal, to anyone without an admin permission. | Consistent with the rest of the app: what you may not see does not exist to you. |
| 2026-10-07 | An invite is a link carrying a 12-character random code. Whoever holds it can join, until it expires, is used up or is revoked. | Simple to share anywhere, including Discord, which is where most communities will be recruited from. Invites addressed to a named person can be added later on the same table. |
| 2026-10-07 | A signed-out visitor to an invite link is sent to sign up and returned to the invite afterwards, through a `next` path that only accepts addresses inside the site. | New people arriving by invite are the main way communities will grow. Restricting `next` to local paths prevents the link being used to redirect people elsewhere. |
| 2026-10-07 | Messages are plain text. Scene posts keep the rich text editor to themselves. | The plan wants messaging plainer than scenes so roleplay has a reason to move into a scene. Plain text also keeps messages safe to render with no sanitising step. |
| 2026-10-07 | In a message box Enter sends and Shift+Enter makes a new line. In the scene composer Return always makes a new line. | Each matches what people expect of that kind of box, and the difference reinforces that a scene post is a piece of writing. |
| 2026-10-07 | Anyone can message anyone by handle. The requests inbox and blocks are not built. | They belong to the trust work and must exist before strangers can find each other through Discover and LFRP. |
| 2026-10-07 | The Lounge is a live chat room with a member list showing who is online, at the product owner's request. | The plan kept chat minimal to avoid becoming Discord. That concern is about roleplay, which stays in scenes; the Lounge is out-of-character space, where a chat room is what people expect. Announcements stays a quiet notice board, and communities still cannot create further channels. |
| 2026-10-07 | Online status comes from a once-a-minute check-in while a tab is visible, stored as `profiles.last_seen_at`. Someone is online if they checked in within 150 seconds. | One column and one small request, with no connection tracking, and it works across several web processes. The plan had deferred presence; it has no opt-out yet, which a privacy setting should add before launch. |
| 2026-10-08 | A library world can be shared by an ID that its owner switches on and off. Anyone holding the ID may copy the world into their own library, or into a community where they hold "Add worlds". | Lets a world's author hand it to a community's admins without being an admin themselves. Sharing is opt-in and revocable, the ID never grants access to the original, and adding to a community still needs that community's permission. It is also the mechanism template worlds will use. |
| 2026-10-08 | The demo community is Demo Town, a plain small town, replacing the Star Trek demo. | A demo should show how the product works without asking anyone to know a setting, and should not lean on someone else's franchise. Databases seeded earlier keep the old demo community until `.data/` is deleted; nothing removes it automatically. |
| 2026-10-08 | Demo Town has one character, a Narrator, who tells both demo scenes. On each start the seed removes every other character owned by a demo account, old or new. | The product owner asked for the demo cast to be removed and replaced by a simple Narrator. The cleanup is limited to characters played by the two demo accounts, so nobody else's character is touched. Posts written by removed characters keep the name they were written under. |
| 2026-10-08 | World templates are data in code (`packages/core/src/templates/catalog.ts`). Using one creates an ordinary library world. | No new tables, and a template cannot be damaged by anything done to a world made from it. Templates created by users would be a later step built on world IDs. |
| 2026-10-08 | Templates use franchise names (Dungeons & Dragons, Star Wars, Jurassic Park, DC Comics, Marvel Comics), by decision of the product owner. | The generic alternative was offered and declined. Each template holds place names and short original descriptions only, with no text from the source works. Using these trademarks on a public service still needs legal review before launch. |
| 2026-10-08 | A community's owner can archive it or delete it. Archiving sets `archived_at`: the community grants no permissions to anyone, joins and posts are refused, and only its members can still see it. Deleting is permanent and requires the community's name to be repeated. | Archive is the safe choice and delete the deliberate one. Making an archived community grant nothing means every permission-gated action stops through the one `authorize` path, with only joining and posting in an existing scene needing their own check. Both are owner-only, read from the Owner role directly so they still work while archived. |
| 2026-10-08 | On start, the demo seed deletes the old Star Trek demo: every community owned by the `demo@worldroot.test` account, then that account. | Requested by the product owner. It is limited to what that one account owns, so a real person's community is never removed, whatever it is named. |
| 2026-10-08 | A public page at `/alternatives` presents original universes for writers who have stepped away from a franchise. The first is Varrowmere, an original school-of-magic setting, and the Wizarding School template is built from it. | Requested by the product owner, for people boycotting Harry Potter and its author. Varrowmere was written from scratch and shares no names, terms or structures with that franchise: students choose their own Hearth, magic is not hidden from ordinary people, and a focus is made by hand. The page names the franchise only to say who it is for. |
| 2026-10-08 | The landing page no longer redirects signed-in visitors to Home. | So the page has one address that always shows it. Signed-in visitors see a button to their Home in place of the sign-in buttons. |
| 2026-10-08 | The platform administrator is named by `WORLDROOT_ADMIN_EMAIL` in the server's environment and made staff on start. If the account does not exist and `WORLDROOT_ADMIN_PASSWORD` is set, it is created. | The first administrator has to come from somewhere, and it must not be a request anyone could send or a credential committed to the repository. The password is used only to create a missing account and is never applied to an existing one. Granting staff is written to the audit log. Staff must have two-factor sign-in before a public launch. |
| 2026-10-08 | Staff carry an Admin badge beside their name, and are made an owner of the demo community on start. | Requested by the product owner. The badge is derived from `users.platform_role` at read time, so it cannot be set or faked through a profile. |
| 2026-10-08 | A profile page at `/u/handle` shows a writer's communities and characters only where the viewer could already see them: communities that are listed or shared, and approved characters in those. Library originals never appear. | A profile must not become a way round a community's privacy. The same visibility rule the rest of the app uses is applied per viewer. Profiles are for signed-in people only for now; whether they are public to the web is a launch decision. |
| 2026-10-08 | "Appear offline" is a profile setting stored as `profiles.hide_online`. Check-ins continue, but the person is never listed as online. | Closes the gap noted when presence was added. Keeping the check-in means turning the setting off takes effect at once. |
| 2026-10-08 | Handles cannot be changed yet. | The plan calls for changes with a cooldown and a redirect from the old handle. Links to profiles use the handle, so that needs doing properly rather than quickly. |
| 2026-10-08 | `WORLDROOT_ADMIN_PASSWORD_SYNC=true` makes the start-up step apply the configured password to an administrator account that already exists. It is honoured only with the embedded local database. | The administrator's account pre-dated the setting, so the configured password was never applied and sign-in failed. Overwriting a password from a settings file is acceptable on a developer's machine and not on a real server, where an administrator must use a proper reset. Each change is written to the audit log. |
| 2026-10-08 | Badges come from a registry in `packages/contracts/src/badges.ts`. Platform badges (Staff, Founder, Premium, Early supporter, Beta tester) show everywhere as filled pills in fixed colours. Community badges (Owner, Admin, Mod) are derived from a member's roles, show only inside that community, and are outlined in its accent. | The product owner asked for WorldRoot staff to be told apart from community admins. Different shapes and colour sources make the two impossible to confuse, and a community cannot restyle a platform badge. Staff and Premium are derived from the account, so they cannot be granted as loose badges or drift out of step. |
| 2026-10-08 | Premium is `users.premium_since`, set by staff by hand from the staff portal. | There is no billing yet and what Premium includes is undecided. The column and badge let the rest be built without committing to a payment provider. |
| 2026-10-08 | A handle can be changed every 14 days. The old handle is kept for its owner in `handle_history`: links to it redirect, and nobody else can take it. | Profile links use the handle, and a released handle is an impersonation risk. |
| 2026-10-08 | Blocking closes direct messages and private-scene invites in both directions and is never announced. A declined message request is refused with the same wording as a block. | Neither a block nor a decline should give the other person something to react to. Blocks do not yet hide people from each other in lounges or shared scenes. |
| 2026-10-08 | A first direct message between people who share no community is a request: up to three messages, then the recipient must accept. Groups can only be formed among people who share a community. | The plan's protection against unsolicited contact. Limiting groups closes the obvious way round it. Staff are exempt so they can contact anyone. |
| 2026-10-08 | DnD mode will be a per-community setting. | Decided by the product owner. |
| 2026-10-08 | The administrator's password from the settings file is applied to an existing account once only. | So a password later changed in the app is not overwritten on the next start. |
| 2026-10-08 | A report stores a snapshot of what it is about. A community's holders of "Review reports" see reports from their community. WorldRoot staff see reports with no community (direct messages, private scenes, profiles) and any report in a category marked as possible harm or law-breaking. | The plan's two jurisdictions. The snapshot means a report still stands after the content is edited or removed. Private conversations are described but not linked, so reviewing a report never means reading the rest of someone's messages. A person can only report what they can see, so reporting cannot be used to probe for hidden content. |
| 2026-10-08 | Closing a report records an outcome but takes no action by itself. Reviewers remove content or members with the existing tools, then mark the report. | Keeps one path for each moderation action, each already audit-logged. Linking an action to the report that prompted it, and appeals, are still to come. |
| 2026-10-08 | Notifications are written by the service that makes the change, in the same transaction, and are shown in the Inbox only. Events with the same group key fold into one unread notification. | The worker that would turn outbox events into notifications needs a PostgreSQL server and has never run; writing them directly works on the embedded database and can never describe a change that was rolled back. Folding keeps a busy scene to one line. There is no email, no push, no per-scene mute and no notification settings yet, and the Inbox dot updates on the next page load, not live. The Lounge and direct messages do not notify: they have their own unread marks. |
| 2026-10-08 | Discover lists communities that are listed and not archived, largest first, with a name search. Looking for RP is one platform-wide board of plain-text listings that lapse after 30 days, three open per person. | The smallest version that lets strangers find each other, now that blocks, message requests and reporting exist. Listings belong to no community, so reports about them go to WorldRoot staff, who can take one down (audit-logged). Not yet built: listings inside a community, linking a character or world to a listing, renewing a lapsed listing, discovering worlds and active scenes, and ranking by anything other than size and date. |
| 2026-10-08 | Core tests allow two minutes for setup. | Each test file starts its own in-memory PostgreSQL and runs every migration; with eighteen files starting together that passed the default ten seconds on the development machine. |
| 2026-10-08 | Formatted long fields are stored as documents in one `docs` JSON column on `characters` and `worlds`, keyed by field name. The existing text columns stay and always hold the plain text. | Replaces the 2026-10-07 decision to leave these fields plain. Nothing that reads the text columns (cards, search, report snapshots, templates, the demo seed) had to change, old records need no conversion, and a field sent as plain text simply has no document. Documents are checked against the allowlist on the way in and again on the way out. Covers a character’s appearance, personality and biography and a world’s description. Locations, community descriptions and rules, profiles' bios and the shorter character fields are still plain text. |
| 2026-10-08 | Uploaded images are profile pictures and character portraits only. Bytes are kept in a folder on the server (`WORLDROOT_MEDIA_DIR`, default `.data/media`) behind a three-method `MediaStorage` interface; a `media` row records each one. | The smallest useful step, with no new service to run. Object storage is one more implementation of the interface. A folder on one server does not work across several web servers and must be backed up with the database. |
| 2026-10-08 | An upload's type is decided from its bytes. PNG, JPEG, GIF and WebP up to 2 MB are accepted; SVG and everything else is refused. Exif, XMP, text chunks and comments are removed by walking the file's structure, with no image library. Images are served to signed-in people only, with `nosniff` and a sandboxing content security policy. | Photos carry GPS positions and author names; a roleplay site must not leak where a writer lives. Doing it by hand avoids a native dependency, at the cost that images are not resized or re-encoded: a 2 MB picture is served whole into a 36-pixel circle, and a file that is a valid image and also something else is not caught. Before a public launch this needs re-encoding and thumbnails, automated scanning for illegal images, and a decision on images in scene posts. Staff can remove any profile picture and any portrait; both are audit-logged. |
| 2026-10-08 | DnD mode is `communities.dnd_mode`, switched by anyone who can manage the community. For now it does one thing: lets participants roll dice in that community's scenes. A roll is made on the server from the system's random source and stored as a `system` post in the story. | The first, self-contained piece of the plan's "dice and custom RP systems". Server-made, uneditable rolls are the part players must be able to trust. Not yet built: character stats and modifiers taken from a sheet, a game master role with hidden rolls, advantage and other roll types, initiative, and dice in private scenes. A roll's author can still remove it, which leaves a visible "removed" line. |
| 2026-10-08 | A second demo community, Demo Dungeon (`/c/demo-dungeon`), is seeded beside Demo Town on the embedded database, with DnD mode on. It is owned by the same demo account, and the platform administrator is made an owner of it too. | Requested by the product owner, to show tabletop-style play. Its setting, Thornwick Vale, is original: it follows the shape of a D&D adventure without any published place, character or text. Its two seeded rolls use fixed numbers so the story written around them reads correctly; every roll made by a person is random. It is created once and never changed again, so edits by its owners survive restarts. Like Demo Town it must not run on a public deployment. |
| 2026-10-08 | The interface takes a Frutiger Aero look in the colours of worldroot.carrd.co: a cream page, caramel accent, and violet and blue kept for glows. It lives in the tokens and in a handful of classes in `globals.css` (`wr-glass`, `wr-popover`, `wr-chrome`, `wr-gloss`, `wr-gloss-light`, `wr-title`). | Requested by the product owner. Three things follow from the palette. Caramel is a light colour, so text on an accent fill is now dark, in every community hue; the accent ramp was re-cut for that and is less saturated than before. Cards are translucent but not blurred, because a blurred element traps the pop-ups inside it behind its neighbours; only the app frame and pop-ups blur. Headings moved to the interface sans (Heebo, as on the site) and the name is set in Pacifico; story text keeps its serif. Reduced-motion and reduced-transparency settings are honoured. |
| 2026-10-08 | The dice animation is decoration over a result that already exists. | The server rolls first; the browser then shows tumbling faces for under a second and settles on the server's numbers. The faces shown while tumbling are picked in the browser and mean nothing. Screen readers hear the result once, in words. |
| 2026-10-08 | Friends are one row per pair in `friendships`, pending until the person asked accepts. Declining, cancelling and unfriending delete the row and tell nobody. Friends may message without a request and see each other's online status; a block ends the friendship and the refusal reads the same as "no such person". | Requested by the product owner, after Discord. Deleting rather than recording a decline means nobody keeps a list of who turned them down. The existing message-request rule stays for strangers; friendship is a second way past it, beside sharing a community. |
| 2026-10-08 | Achievements are a separate registry from badges. They are stored in `user_badges`, earned automatically, checked after the action that could earn them, kept once earned, and shown only on the profile. | Requested by the product owner ("10+ characters, worldbuilder"). Keeping them off the line beside a name leaves that line for badges that say something about trust: Staff, Premium, community standing. A failed check never fails the action; it is logged and the badge is earned next time. |
| 2026-10-08 | Profiles gain a banner image, a hue and a status line. The profile page takes the hue the way a community page takes its community's. | Requested by the product owner, after Discord. The hue runs through the same generated ramp as communities, so no choice can make text unreadable. Banners go through the same checks and metadata stripping as other images, and staff can remove one. |
| 2026-10-08 | The side rail lists Home, a Resources section (Discover, Scenes, Library) and every community the person belongs to. The Inbox is an icon at the top right. A community's member list stands beside every page of the community. | Requested by the product owner, after Discord. The plan warned against becoming Discord with roleplay features; these are navigation and presence, not channels, and roleplay still lives in scenes. The phone's bottom bar now ends in Communities, since the Inbox moved up. |
| 2026-10-08 | The logo is the product owner's book-and-roots mark. Its page colours are fixed; its spine and roots take the text colour so they show on a dark page. | The mark's terracotta (#D77B57, #E9A37E) is warmer than the caramel of the site palette. The interface accent was left as it was; whether to move it toward the logo is the product owner's call. |
| 2026-10-08 | Badges are icon-only, with the name shown on hover or keyboard focus. Platform badges other than Staff appear on profiles only; Staff appears beside a name everywhere. A community's Owner, Admin and Mod badges still appear inside that community. | Decided by the product owner. Community standing was kept beside names inside the community because it is not a profile badge and tells members who can moderate; it follows the same icon-only rule. The name stays in the page for screen readers. On a touch screen there is no hover, so a badge's name is seen by tapping it or on the profile. |
| 2026-10-08 | Dice are drawn in their real shapes: the d6 is a 3D cube, the others are faceted drawings turned in 3D as they tumble. A dice theme is five colours; a person's choice is `profiles.dice_theme`. Three themes are free. Four more are in the registry as locked previews and the server refuses them. | Requested by the product owner, who wants themes that can later be earned with points or bought. The registry, the stored choice and the server-side refusal are the parts a shop will need; ownership, points and payments are not built and need decisions first (see below). A theme changes only how the roller sees their own dice: the roll in the story looks the same to everyone. |
| 2026-10-08 | A badge's meaning is shown in a floating label, not by widening the badge. | Widening pushed the neighbouring badge, which could wrap to the next line and slide out from under the pointer, so the two flickered. Reported by the product owner with Staff beside Owner. |
| 2026-10-08 | Staff manage an account from its own page: badges, Premium, removing a picture or banner, signing it out everywhere, and suspending or restoring it. A suspension is `users.suspended_at` with a required reason; it ends every session and is checked on every page and API request. | The staff portal only had badge switches and a link to the profile. Suspension removes nothing the person wrote, so it can be undone exactly. Staff cannot suspend themselves or another member of staff: who is staff is set in the server's settings, and that stays the only way to change it. Deleting an account, and telling the person by email, are not built. |
| 2026-10-09 | Dice styles are chosen under Settings > Customization, not in the dice tray. | Decided by the product owner. The tray is for rolling; the tray keeps one link to the setting. Customization is where other personal cosmetics will go, and where a shop would hand off to. |
| 2026-10-09 | A link to a profile from inside the app opens the profile in a pop-up, using an intercepted route in a parallel `@modal` slot. The address still changes to `/u/handle`, and opening that address directly or refreshing shows the full page. | Requested by the product owner, after Discord. One component renders both, so they cannot drift apart. Keeping the address real means a profile can still be linked, bookmarked and opened in a new tab. Following a link inside the pop-up closes it. |
| 2026-10-09 | There are nineteen achievements. A profile shows only those earned; the full list with progress is the person's own Achievements tab in Settings. Worldbuilder and Cartographer are also badges, by sharing a key between the two registries. | Decided by the product owner. Progress is private: only the person sees what they have not earned. Each achievement names what it counts and its target in one table, so adding one is a line in each registry. |
| 2026-10-09 | A dice roll is one continuous animation: each die travels in, bounces three times and rolls to a stop, with travel and turning sharing one easing. The faces change while the die moves and hold on the real numbers before it stops. | The earlier version looped a tumble and then cut to a separate landing, which read as two unrelated movements. The result is still made by the server before anything moves. The story's live update is held back until the dice are still. |
| 2026-10-09 | Interface text, comments and names use American spelling. | The product owner writes American English and asked for consistency. Earlier entries in this log are left as written. |
| 2026-10-09 | Staff can switch the whole site to a look: Pride, Trans pride, Halloween, Easter or Holidays. It is one row in a new `platform_settings` table, read by the root layout and written to `<html data-season>`. A look recolors the logo's pages, the WorldRoot name and a stripe across the top of every page, and nothing else. | Requested by the product owner. Keeping a look to those three places means no look can make text or a control unreadable. The name's colors are pulled toward the text color so pale bands such as white and yellow still read as lettering in both themes. Looks are switched by hand; nothing turns one on or off by date. The app icon in a browser tab does not change. |
| 2026-10-09 | Settings has a Badges tab listing every badge, held or not, with how it is come by. An achievement that is also a badge is marked. On a profile, the staff link to manage the account is at the foot. | Requested by the product owner. Each badge's explanation lives in the badge registry beside its name. |
| 2026-10-09 | WorldRoot staff are called Rootwardens, and platform badges take names from the World Tree: Seedbearer (founder), Deeproot (early supporter), Seedling (beta tester). The achievements Wordsmith and Regular become Skald and Three branches. The keys in code and in the database are unchanged (`staff`, `founder`, and so on). | The product owner is building WorldRoot's identity around Yggdrasil and asked for a more thematic name for staff. Wherever the name matters for trust (the badge's hover text, reports, the suspension notice, refusals) it is paired with the plain words "WorldRoot staff", so nobody is left guessing who has authority. Premium and the community badges (Owner, Admin, Mod) keep their plain names: Premium is not yet defined, and community standing has to be unmistakable. |
| 2026-10-09 | The report form is a dialog rendered into the page body, not a panel hanging from the Report link. | A panel positioned from its link was clipped whenever the link sat inside something that scrolls or clips: the profile pop-up, the chat, the member list. Reported by the product owner. |
| 2026-10-09 | A community's copy of a world can be edited from the community's own pages by whoever holds the matching permission: "Manage worlds" for the world's details, "Create locations" to add places, "Manage locations" to edit them. | The service layer had allowed this from the start, but there were no screens: a world could only be edited in its author's library, so once copied into a community nobody could change it, the owner included. Reported by the product owner. Each page asks one function, `worldPowers`, what the viewer may do, and shows only those controls; the edit pages return 404 to anyone else. Edits are audit-logged, and an archived community's worlds are closed. Holding "Manage community" does not by itself allow editing worlds: the three permissions are ticked on a role like any other. Removing or reordering locations is still not built, in a library or a community. |
| 2026-10-09 | Headings, buttons, tabs, menu items, field labels and the names of things (badges, achievements, permissions, genres) are in Title Case, with every word capitalized. Descriptions, hints and messages stay as sentences. | Decided by the product owner. Controls take it from one CSS class each (`capitalize`), so words chosen in code are covered; headings and names are written that way in the source. Two buttons opt out because they carry a dice notation or an @handle. Headings that show a person's own words (a character's name, a scene's title) are never transformed. |
| 2026-10-09 | A site look is a full theme: besides the logo, name and stripe it sets the default accent hue, relights the page background in the look's colors, colors page titles, and adds ten slow-drifting shapes (hearts, bats, eggs, snow). | The product owner found the first version too slight. Text colors and surfaces are still untouched and communities keep their own accent, so contrast is the same in every look. The shapes sit behind the page, ignore the pointer, stop for reduced motion and are removed for reduced transparency. |
| 2026-10-09 | The stripe for a site look is a ribbon: blended, slowly flowing colors with a shaped lower edge per look (wave, drips, scallops, zigzag). Titles use a hand-picked run of colors per look, one set for the light page and one for the dark, through `light-dark()`. The page background uses four broad pools of color instead of six small ones. | The product owner asked for a more distinctive bar and better gradients. Titles had been made by mixing each flag color toward the text color, which turned them brown; fixed colors chosen for lettering read cleanly and keep their contrast. `light-dark()` needs a browser from 2024 or later; an older one shows the title in its usual accent color. |
| 2026-10-09 | The top of the page carries an illustrated banner for the site look, replacing the colored stripe and ribbon. Halloween is a night scene with pumpkins, ghosts and a witch; Pride and Trans Pride are one long rippling flag. The Easter and Holidays looks are replaced by Spring and Winter. | Decided by the product owner, who found the ribbons poor and wanted the two seasonal looks to be about the season, not a festival, so they suit everyone. Each scene is an SVG tile drawn in code and repeated across the width, so there are no image files and it fills any screen. A setting saved as `easter` or `holidays` now reads as the standard look. The banner sits in the page and scrolls away; it is decoration and hidden from screen readers. |
| 2026-10-09 | The site look follows a calendar unless staff hold one on. The setting is `auto` (the default), a look, or `none`. The calendar is a short table in `packages/contracts/src/seasons.ts`: Halloween in October, Winter December to February, Spring March to May, Pride in June, Trans Pride on March 31 and November 13 to 20. | Requested by the product owner. The look is worked out from the date on every request, so nothing has to run at midnight and no job can be missed. Dates are read in UTC and the seasons are the northern hemisphere's, so a visitor far from UTC sees a change some hours early or late, and southern-hemisphere writers see the opposite season. Holding Standard on turns every look off. A stored value this version does not know reads as automatic. |
| 2026-10-09 | Signing in with Discord or Google never joins itself to an existing account by matching email. A provider is connected to an existing account only from Settings, by someone already signed in. | WorldRoot does not verify email addresses, so an account with a given email could have been made by anyone. Joining by email would let someone register a victim's address with a password, wait for the victim to sign in with Google, and share the account. The cost: someone who made a password account and later presses "Continue With Google" is told to sign in the old way and connect it. |
| 2026-10-09 | Deployment is a `Dockerfile` at the repository root, with `railway.json` pointing Railway at it. The container applies migrations, then starts the site; a failed migration stops it starting. Pictures live on a mounted volume at `WORLDROOT_MEDIA_DIR`. `/api/health` reports whether the site can reach its database. | The product owner chose Railway and wants to be able to leave it. A container builds the same on any host, and nothing else is Railway-specific. Neither the image nor the PostgreSQL code path has been run: the development machine has no Docker and no PostgreSQL server, and every test so far used the embedded database. The first deploy is the first real test of both. |
| 2026-10-09 | "Get the app" is a page that installs WorldRoot as a web app through the browser, not a download of an installer. | The product owner asked for a download link for an `.exe`. No such file exists, and making one means wrapping the site in Electron or Tauri, building it per platform, and either paying for code signing or having Windows warn every user that the program is unrecognized. An installed web app gives the same result on Windows, Mac, Android and iPhone with nothing to maintain. The manifest gained 192 and 512 pixel PNG icons, which browsers require before offering install; they were rendered from `icon.svg` and must be rendered again if the logo changes. A wrapped desktop build remains possible once the site has a permanent address. |
| 2026-10-09 | A privacy policy (`/privacy`) and terms of service (`/terms`) exist, written by the development assistant to describe what the code does, not reviewed by a lawyer. | Google and Discord both ask for these links before sign-in can be offered to the public. Every statement in the policy matches current behavior: no analytics, no ads, IP address and browser kept per session, image metadata stripped, account deletion by request because there is no button. Change the page and `LEGAL_UPDATED` in the same commit as any change to what is collected. The terms name no governing law or legal entity because neither has been decided. The contact address comes from `WORLDROOT_CONTACT_EMAIL` so no personal address is in the source. Both need a legal review before a wide public launch. |
| 2026-10-09 | The web app applies database migrations itself when it starts, on PostgreSQL as well as the embedded database. | The first Railway deploy came up with an empty database. Railway had made a service per workspace app and was not running the `Dockerfile` start command that called `pnpm db:migrate`, so sign-in failed and the administrator was never created. Migrating on start works whatever command the host runs. A failed migration fails the health check, so the host keeps the previous version. This is safe for one web server; several starting together could race, and at that point migrations should move to a release step. |
| 2026-10-09 | The cross-site guard on API requests compares the browser's Origin with the site's configured address (`BETTER_AUTH_URL`) and the Host header, not with the request's own URL. | Behind Railway's proxy the request URL is `localhost:8080`, so every save on the live site was refused as cross-site. A page on another site cannot change the Host header a browser sends, so the check is as strict as before. `BETTER_AUTH_URL` must therefore always be the address people actually use. |
| 2026-10-09 | The demo communities can run on a real server with `WORLDROOT_DEMO=on`, and the demo account never has its published password there. | The product owner wanted Demo Town, Demo Dungeon and the demo account on the live site. The password in `DEMO_ACCOUNT` is in the source and the README, so on a public site anyone could sign in as the owner of both communities. On a real server the account's password is `WORLDROOT_DEMO_PASSWORD` if set, otherwise a fresh random value on every start, which also replaces the published one if it was ever applied. A shared sign-in open to the public was not built: it would let anyone post, message and upload under one account on an adults-only site with no way to tell people apart. |
